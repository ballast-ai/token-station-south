# Release 0.51.1: a guest trap is a clean error, and the component survives it

Status: prepared on branch `fix/guest-trap-reentry` (based on `origin/main` `dbbfcc8`, release 0.51.0 plus CI-only
changes); not tagged. The tag and the host re-pin are separate steps.

Date: 2026-10-09

Records: the host's gap #101 (found 2026-10-09 in the host's `gateway/tests/embeddings_guest_trap.rs`),
[release 0.51.0](2026-10-09-release-0.51.0.md), [boundary record](2026-09-30-host-zero-vendor-boundary.md) §13.12
(Q47).

## 1. What this release carries

Two defects in `south-provider-runtime`, both visible only when a guest traps, and nothing else. No package, contract,
manifest, public API or guest-linked crate changes: `south-contracts`, `south-provider-api` and
`south-component-conformance` stay at 0.50.0, so **Q47 does not apply** and every package keeps its version,
`manifest.json`, `component.wasm` and `south_runtime`. The release bump is the workspace-versioned side only
(`[workspace.package] version`, `compatibility.json` `release.version`, the requirements on `south-core`,
`south-testkit`, `south-provider-conformance`, `south-north-codec` and `south-transport-reqwest`, the literal in
`south-task-core`'s version test, `fuzz/Cargo.lock`). The only new dependency of the runtime is `wasmtime-wasi-io`, which
`wasmtime-wasi` already pulled in.

## 2. The defects

The host reproduced them with the released `embeddings-openai-compatible` package (default 64 MiB guest memory): a text
input of 8 MiB passes and one of 9 MiB traps (out of memory in the guest). Then:

1. The host's request task **panicked** with `Cannot start a runtime from within a runtime`; the client saw a dropped
   connection.
2. **Every later call** to that package failed (`component state is poisoned`, and after the first fix
   `wasm trap: cannot enter component instance`) until the process restarted.

**Layer 1: the panic.** `wasmtime_wasi::p2::add_to_linker_sync` implements the `wasi:io` functions of the synchronous
bindings by running the async implementation under `Handle::block_on` whenever the calling thread is inside a tokio
runtime (`wasmtime-wasi` 49.0.2, `src/runtime.rs` `in_tokio`, `src/p2/host/io.rs`). A host calls a component from a
request task, so that is always the case. A normal call never touches a WASI stream. A guest that traps by panicking or by
failing an allocation first writes the message to stderr and flushes it with `blocking-flush`, and that call panics the
tokio worker. A trap that is not preceded by a message (an infinite loop and the epoch deadline) returned cleanly.

**Layer 2: the dead instance.** After *any* trap, including the clean deadline trap, wasmtime refuses to enter that
instance again (`cannot enter component instance`). The runtime kept using it as the component's shared instance. A
panic inside the call also poisoned the `Mutex` for good. The runtime's own tests ended the trap cases with
`let _ = …` and never asserted that the following call worked.

All four worlds go through `LoadedComponentV1::call`, so all four are affected by layer 2. A stream has an instance of its
own: layer 1 reaches it, layer 2 does not (the owner drops a trapped stream and opens another).

## 3. The fix

### 3.1 Layer 1: non-blocking `wasi:io` functions (`src/nonblocking_io.rs`)

After `add_to_linker_sync`, the linker re-registers the `wasi:io/streams` and `wasi:io/poll` functions with
implementations that **delegate to the same `wasmtime-wasi-io` async implementations and drive their futures on the
calling thread without ever parking it** (`finish`: poll, re-poll while the future woke itself, otherwise give up). That
is enough because a component here has nothing to wait for: stdin is closed and stdout and stderr discard their input
(`WasiCtxBuilder::new().build()` gives `empty()` streams), and `wasi:sockets` and `wasi:http` are refused at load. A stdio
future is ready the first time it is polled. No thread is spawned and no runtime is entered, so it behaves the same in
a multi-thread runtime, a current-thread runtime and on a thread with no runtime.

A future that is not ready (only a guest sleeping on a clock produces one) is answered with a trap, and a panic while
polling it (tokio's clock timer panics outside a runtime, or in one built without `enable_time`) is caught and answered
the same way: `the guest waited on host I/O that cannot complete: this sandbox has no blocking waits`. Before, that call
would hold a host thread for as long as the guest asked, beyond what the epoch deadline can interrupt. **This is a
behavior change for a guest that sleeps through WASI**; no shipped package does (they are pure codecs), and it is pinned
by the `*_sleep` tests. A caught panic still prints its message through the process panic hook.

**Why this and not the alternatives**

| Option | Verdict |
|---|---|
| (a) Replace the blocking functions in the linker | Chosen. Zero thread overhead; works on every runtime flavor |
| (b) `tokio::task::block_in_place` around the call | Rejected. It panics on a current-thread runtime, which a host's `#[tokio::test]` is, and it still parks a worker for the whole guest call |
| (c) A scoped thread per call (the host's prototype) | Rejected. Measured: spawn and join alone cost 19 µs here, so a 9 µs call becomes 31 µs (3.4×), and a stream chunk (5 µs, one call per chunk) about 24 µs |

**The `in_tokio` call sites of `wasmtime-wasi` 49.0.2 and how each is handled** (found by grepping `in_tokio`,
`block_on` and `try_current` in `wasmtime-wasi` and `wasmtime-wasi-io`; the latter has none):

| Site | Functions | Handling |
|---|---|---|
| `p2/host/io.rs`, output stream | `drop`, `blocking-write-and-flush`, `blocking-write-zeroes-and-flush`, `blocking-flush`, `blocking-splice` | replaced |
| `p2/host/io.rs`, input stream | `drop`, `blocking-read`, `blocking-skip` | replaced |
| `p2/poll.rs` | `poll`, `pollable.ready`, `pollable.block` | replaced |
| `p2/host/filesystem/sync.rs` (26) | every `descriptor` and `directory-entry-stream` method | unreachable: a guest can only get a descriptor from `preopens`, and there are none; it cannot forge a handle |
| `p2/host/tcp.rs`, `udp.rs`, `udp_create_socket.rs`, `p2/ip_name_lookup.rs` | sockets and name lookup | unreachable: `wasi:sockets/` imports are refused at load |
| `p0.rs`, `p1.rs` | preview 0 and 1 adapters | not linked (only the preview 2 `add_to_linker_sync` is called) |
| `runtime.rs` | `in_tokio`, `with_ambient_tokio_runtime` | only reached through the sites above |

Clock `now` and `resolution` do not need a runtime. The only other tokio use on a path the guest can reach is the clock
pollable's timer (`monotonic_clock::subscribe_*`), which is covered by the `poll` row.

### 3.2 Layer 2: the shared instance is replaced after a guest error

`main` holds the instance and a `stale` flag. When a guest call returns an error (a trap, the deadline, a failed
allocation, an error from a host function, `exit`), the instance is marked stale and the **next call** instantiates a new
one before running. The one error that does not mark it is the world mismatch (`call_parse_response` on an embeddings
component), which is raised before the guest is entered; it is now a private error type so that a caller's mistake costs
nothing.

- **Bounded:** the new instance comes from the same `instantiate` as a stream's, under the same epoch deadline and memory
  limit, so start code that traps or loops cannot hang the host or exhaust it. If it fails, the call returns that trap and
  the next call tries again.
- **Lazy, not eager:** nothing is paid until a call follows a trap, and a failure to rebuild is reported to the caller that
  needs the instance rather than swallowed.
- **No poisoning by construction:** the lock is not held across anything that can panic except the operation itself,
  whose only host code is the caller's `SecretSignerV1`. A signer that panics poisons the mutex; the next call takes the
  guard anyway, clears the poison and replaces the instance. The guard is dropped before the result is converted.
- Per-stream instances are unchanged.

Cost, measured: the call that follows a trap takes 39 µs against 9 µs for a normal call, once per trap.

## 4. Evidence

### 4.1 The runtime tests (`crates/south-provider-runtime/tests/guest_trap_recovery_v1.rs`)

Each test drives a real trap through the real runtime and asserts that it is an `Err` of the right kind (not a panic), then
that the next call on the same loaded component succeeds, twice over. Three places a host calls from × three carriers ×
the faults: a guest panic, a 256 MiB allocation against 64 MiB, an infinite loop (500 ms deadline) and a sleep. The test
guests gained the matching switches (`__panic`, `__grow_mb`, `__hang`, `__sleep_ms`) on the embeddings config and on a JSON
stream chunk.

| | multi-thread tokio | current-thread tokio | no runtime |
|---|---|---|---|
| provider panic / out of memory / deadline / sleep | red → green | red → green | red → green |
| embeddings panic / out of memory / deadline / sleep | red → green | red → green | red → green |
| stream panic / out of memory | red → green | red → green | green (no layer 1 there, a stream is not reused) |
| stream deadline | green | green | green |

Red on `origin/main`: 22 of the 27 original cases fail (the task panics with `Cannot start a runtime from within a
runtime`, or the next call fails with `cannot enter component instance` or `component state is poisoned`); all pass after
the fix, with the sleep cases and a signer-panic case added (34 tests). The existing trap tests in `wasm_component_v1.rs`
now assert the next call too.

## 5. Open items

- **Trap versus guest error at the seam (for the host; not done here).** `CallErrorV1` already tells `Component` (the guest's
  own error payload), `Deadline` and `Trap` apart. The flattening is one layer up, in `south-component-conformance`'s
  `sandbox::seam_error`, which maps a trap into the same `ErrorEnvelope(Internal, 500)` as a guest-reported error, so a host
  cannot tell them apart and echoes the trap text in a 502 body. The text is wasmtime's trap message and, for a trap
  inside guest code, a backtrace with the guest's function names; it holds no guest memory contents. Fixing it means
  changing a type or a function of `south-component-conformance` (or adding a `CallErrorV1` variant, a source break for
  exhaustive matches), and the first would change that crate, which every component links: **Q47 would apply and all
  eighteen packages would take a patch bump**. A host can do it today by matching `CallErrorV1` itself before
  `seam_error`, and by not echoing `Trap` text.
- A guest that sleeps through WASI is now a trap (§3.1). Reversing that needs a real blocking wait bounded by the call
  deadline, which no shipped package needs.
