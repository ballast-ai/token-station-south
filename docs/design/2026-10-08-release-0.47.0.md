# Release 0.47.0: the embeddings world

Status: prepared on branch `feature/embeddings-world`; not tagged. The tag and the host re-pins are separate steps.

Date: 2026-10-08

Records: [embeddings contract](2026-09-30-embeddings-contract.md) (accepted with the v1 scope of §15),
[boundary record](2026-09-30-host-zero-vendor-boundary.md) §13.6 (the declared-runtime discipline).

## 1. What this release carries

The `embeddings-adapter-v1` world and its first three packages (§2), on top of 0.46.0. The kernel pin, the
`kernel_contracts` and every south contract number other than the new `embeddings` stay as 0.46.0 released them.

## 2. The embeddings world

New: WIT package `token-station:embeddings-adapter@1.0.0`, world `embeddings-adapter-v1`, embeddings contract 1
(`compatibility.json` `contracts.embeddings` 1), the gate ② suite `south.embeddings-component.v1`, the pure host
functions `extract_vectors_v1`, `check_embeddings_response_v1` and `render_vectors_v1` with the northbound parser in
`south-contracts`, and three packages:

| Package | Version | Families | Auth arms | Capabilities |
|---|---|---|---|---|
| `embeddings-openai-compatible` | 1.0.0 | `openai-compatible`, `azure-openai-v1` | `bearer`, `header_secret` | `embed`, `batch`, `dimensions`, `token_ids` |
| `embeddings-gemini` | 1.0.0 | `gemini` | `header_secret` | `embed`, `batch`, `dimensions` |
| `embeddings-vertex` | 1.0.0 | `vertex-ai` | `bearer` | `embed`, `dimensions` |

Each package is a thin wasm guest over the native reference gate ② was frozen against. Its sandbox parity test runs
the suite over the built `component.wasm` (and writes the gate ② report the release publishes), requires the same
outcome for every check as the native run, and requires every ABI answer of every fixture case to be the same string
inside and outside the sandbox.

`embeddings-vertex`, the third package the record's §11 E1 suggests, ships in this release too (§2.2), so every package
E1 names is here.

`compatibility.json` moves to `schema_version` 6: it gains `contracts.embeddings`, the
`embeddings_component_v1_suite_id` / `embeddings_component_v1_suite` conformance fields and the top-level
`embeddings_component_capabilities` table, as `task_component_capabilities` moved it from 3 to 4.

### 2.1 v1 scope (record §15) and its three refusals

Contract 1 carries text and token-id inputs only; `Media` and `TextBlob` arrive with contract 2, together with the
`media` capability word, the `request.media` row and `ReferenceIntegrity`. Three things a host serves today are
therefore refused or left in place, on purpose:

1. **Media inputs.** The northbound parser recognizes a `data:<media type>;base64,` input and returns a media-input
   refusal, distinct from a malformed request, so the host answers 400 before admission with zero upstream calls.
   Rows serving multimodal Gemini models stay on the native arm until contract 2.
2. **Large request views.** Without `TextBlob`, a request view above the runtime payload limit (16 MiB) cannot cross
   the sandbox; the host answers 413 before admission. The native arm accepts up to the host's 32 MiB JSON body limit,
   so this is an intentional dual-run difference.
3. **GLM, GLM Coding and Copilot are not migrated.** They stay on their native paths (record §11) and remain items of
   the host's vendor-identifier count until their packages declare embeddings support.

The record's §11 lists the other intentional differences, including two added with these packages: an explicit `null`
for `dimensions`, `encoding_format` or `user` is not forwarded by the component (the native arm forwards the client
body, nulls included), and the Gemini component percent-encodes the model in the URL (identical for names made of
`[A-Za-z0-9._-]`).

The world has no `ChatRequest`, so gate ① refuses `host_values` on an embeddings package, as on the task worlds. It
admits the two sources of `ProviderConfig.declared`, a family's `config_schema` and exported credential attributes
(0.46.0's value channel, boundary record §13.8), which the task worlds refuse; §2.2 and the record's §16 say what is
admitted and why.

### 2.2 `embeddings-vertex` and the value channel in this world

`embeddings-vertex` 1.0.0 (family `vertex-ai`) is Vertex AI's `:predict` dialect, transcribed from the host's native
Vertex arm: one text input per request (a batch or a token-id input is a capability error before admission),
`{"instances": [{"content": …}]}` with `parameters.outputDimensionality` for `dimensions`, the vector locator
`Array { /predictions, /embeddings/values }`, immutable paths `["instances"]`, no fallback estimate, and usage
`Reported` as the sum of each prediction's `statistics.token_count` rounded half away from zero, with
`per_input_tokens`. Its README in `fixtures-embeddings-vertex/` cites the native code each expectation comes from.

The package needs two things the world did not admit before this release, and the record's §16 adds exactly those:

- **Gate ①.** An embeddings package may declare a family's `config_schema` and export credential attributes, the two
  sources of `ProviderConfig.declared` (0.46.0's value channel, boundary record §13.8), under the provider world's
  rules. `endpoint`, `host_values`, the instance declarations, `signing`, `stream_framing`, `usage_evidence` and
  `request_facts` stay provider-only; the task worlds still refuse both sources. The suite gains
  `UndeclaredValuesIgnored`.
- **Its values.** Config keys `region` (required) and `project` (optional, the operator's override), and the attribute
  `project_id`, exported from the non-secret field the service-account key file's `/project_id` imports.

**The credential recipe** reproduces the host's Vertex mint (`VertexMint`, `sign_vertex_assertion`): an RS256
`jwt_sign` step over the key file's `private_key` with `iss` = `client_email`, `scope` =
`https://www.googleapis.com/auth/cloud-platform`, `aud` = the token step's endpoint, `iat` = now and `exp` = now + 600,
then an `oauth2_token` form step (`grant_type` jwt-bearer, `assertion`) to `https://oauth2.googleapis.com/token`,
presenting `access_token` until `expires_in` later; it does not rotate, and 4xx / 5xx take the defaults
(`reauth_required` / `transient`), the host's classification. `refresh_margin_seconds` 300 is the host's
`REFRESH_BUFFER_SECS`; gate ① requires the margin to be shorter than the shortest validity, so the recipe declares
`min_ttl_seconds` 301, which changes nothing for Google's 3599 s tokens. The claims are equal JSON in canonical order
(boundary record §13.3). Recipes are enabled only for first-party packages verified by digest (boundary record §3.4
rule 5), and the operator confirms the one endpoint.

**Confinement.** The host passes the location's API origin as `base_url`
(`https://{region}-aiplatform.googleapis.com`, or `https://aiplatform.googleapis.com` for `global`) and the component
appends `/v1/projects/{project}/locations/{region}/publishers/google/models/{model}:predict`, so `EndpointConfinement`
holds unchanged. A base URL that is a Vertex AI origin other than the location's is refused before admission; any other
(a proxy, a test server) is used as given. The record's §16 gives the reasons, and its §11 the intentional differences
from the native arm.

### 2.3 E-Q5: the community host

The contract's usage vocabulary has one host consumer today. As ruled for E-Q5 (the same ruling as the image world's
Q5), this release states in writing: **a synchronous embeddings implementation in the community host is
recommended** (P21 §7). Until a host lands it, `compatibility.json` records `embeddings_component_capabilities`
`embeddings_v1` as `not_verified` for both `token-station` and `token-station-server`; a gate ② pass of the packages is
not host adoption.

### 2.4 E-Q1: the erasure path on a 2048 × 3072 batch

Measured once with `cargo test --release -p south-component-conformance --features sandbox --test
embeddings_payload_measurement -- --ignored --nocapture` on an Apple Silicon laptop (Apple M5 Max, 128 GB), against
the built `embeddings-openai-compatible` component under the default runtime limits (payload 16 MiB, memory 64 MiB,
call deadline 2 s), on this branch before it was rebased onto 0.46.0; the rebase changed no embeddings code. The
bodies are synthetic OpenAI embeddings responses (values uniform in ±0.05, written as the shortest decimal that
round-trips the f32, or as base64 of the little-endian bytes); each timing is the fastest of three runs. "Extract" is
`extract_vectors_v1` (parse, extract, erase); "component" is the sandboxed `parse-embeddings-response` over the erased
skeleton.

| Body | Size | Extract | Skeleton | Component | Render to float / base64 | Whole body into the sandbox |
|---|---|---|---|---|---|---|
| 2048 × 3072, float | 74.4 MiB | refused, `body_too_large` (above the 64 MiB response cap) | — | — | — | refused, above 16 MiB |
| 2048 × 3072, base64 | 32.1 MiB | 128.7 ms | 107,546 B | 0.9 ms | 133.2 ms / 10.3 ms | refused, above 16 MiB |
| 1024 × 3072, float | 37.2 MiB | 63.8 ms | 53,272 B | 0.4 ms | 77.8 ms / 26.0 ms | refused, above 16 MiB |
| 432 × 3072, float | 15.7 MiB | 26.7 ms | 22,464 B | 0.2 ms | 33.0 ms / 10.9 ms | trapped (`unreachable`) inside the 64 MiB memory limit |
| 368 × 3072, float | 13.4 MiB | 23.4 ms | 19,136 B | 0.2 ms | 30.1 ms / 9.8 ms | 49.7 ms |

Findings:

- **Erasure is practical; E-Q1 is not reopened.** On the largest body either path can take (2048 × 3072 base64,
  32.1 MiB) the host extracts and erases in about 130 ms and the component parses a 105 KiB skeleton in under 1 ms,
  far inside the 2 s call deadline.
- **The alternative cannot carry the batch.** Its whole body does not cross the 16 MiB payload limit for any
  2048 × 3072 batch, float or base64. Under the limits as they are, the largest float batch whose body fits is 432
  rows at 3072 dimensions, and the guest traps parsing it inside its 64 MiB memory; the largest it parsed whole was
  368 rows (49.7 ms). The alternative would also have to return the vectors across the boundary, which this
  measurement does not include. Choosing it would mean raising this world's payload limit (to at least 33 MiB for the
  base64 batch, 75 MiB for the float one) and its memory limit (64 MiB held 368 of 2048 rows), and giving up byte
  pass-through.
- **The 64 MiB response cap binds before either path.** A float 2048 × 3072 response written as shortest f32 decimals
  is 74.4 MiB, above `MAX_BINARY_RESPONSE_BODY_BYTES` (the host's binary transport cap), so `extract_vectors_v1`
  refuses it. At 3072 dimensions the float form stays under the cap up to roughly 1,760 rows; base64 carries the full
  batch. Upstreams that print more digits per value reach the cap sooner. This is a property of the cap, not of
  erasure, and is recorded for the hosts' batch limits; no contract change follows from it in this release.

## 3. Package identities and `south_runtime`

The three embeddings packages declare `south_runtime` 0.47.0: no earlier runtime knows the world, so this is the oldest
runtime that admits them, and a host claiming 0.46.0 refuses them through the declared runtime alone
(`the_embeddings_packages_declare_the_first_runtime_with_the_world`).

The world added modules to `south-contracts`, `south-provider-api` and `south-component-conformance`, which every guest
links. A same-path rebuild of the fourteen other packages at `v0.46.0` and on this branch before the release commit
(workspace still 0.46.0) gave a different `component.wasm` for every one, so each published 0.46.0 identity retires,
or the release's digest-stability check would refuse it
(`the_embeddings_world_retires_every_published_046_package_identity`). Their behavior is unchanged, and none needs
anything newer, so each keeps `south_runtime` 0.46.0 and `scripts/check-declared-runtime.sh` loads them in a checkout
of `v0.46.0`.

## 4. Hosts

**Breaking on re-pin**: new enum variants `CheckV1::LocatorResolves` and `CheckV1::NamedRowAssertion`, and
`ManifestErrorV1::EmbedCapabilityRequired`. The kernel pin and `HostRangeV1.kernel_contracts` do not move. A host
that wants the embeddings packages adds `embeddings` 1 to its range's `contracts` and routes the world through
`SandboxedEmbeddingsComponentV1`; a host that does not can keep its range, and the loader refuses the three packages by
their contract.
