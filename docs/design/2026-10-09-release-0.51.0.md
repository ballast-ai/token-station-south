Status: prepared on branch `feature/embeddings-contract-2`; not tagged. The tag and the host re-pins are separate
steps.

Date: 2026-10-09

Records: [embeddings contract](2026-09-30-embeddings-contract.md) §17 (contract 2, ruled by lv on 2026-10-09, with E-O2),
[boundary record](2026-09-30-host-zero-vendor-boundary.md) §13.6 (the declared-runtime discipline) and §13.12 (Q47, the

## 1. What this release carries

On top of 0.50.0: embeddings contract 2, which carries media inputs inline and bounded, independent of `contracts.media`
and of the image world; `embeddings-gemini` 1.1.0, the first package to speak it (so the Gemini multimodal embedding
models can move to the component and the host can delete its native Gemini arm); and, under Q47, the new versions of the
three crates every component links and the patch bump of the sixteen other packages (§5). The kernel pin and the
`kernel_contracts` are unchanged; `compatibility.json` records `contracts.embeddings` 2 and `release.version` 0.51.0.

## 2. Contract 2 in one page

- **The input.** `EmbeddingInputV1::Media { media_type, data }`, wire `{"media":{"media_type":"image/png","data":"…"}}`.
  `data` is the client's base64 text after the first `;base64,`, neither decoded nor validated, so the Gemini body keeps
  the client's string byte for byte. Contract 1's wire shapes are unchanged (golden tests untouched).
- **The parser.** `parse_embeddings_request_v2` runs `parse_embeddings_request_v1`'s checks in the same order and differs
  in one step: a `data:<media type>;base64,` string becomes a `Media` input instead of the media refusal. A host routes a
  request through v2 when the routed package declares `media`, through v1 otherwise.
- **Versioning at the host seam.** `EMBEDDINGS_CONTRACT_VERSION` stays 1; `EMBEDDINGS_CONTRACT_VERSION_V2` is 2 and
  `EMBEDDINGS_CONTRACT_VERSIONS` is `[1, 2]`, a host's range. `EmbeddingsRequestV1::new` is the contract 1 constructor and
  refuses media; `new_v2` accepts it; `carries_media()` and `minimum_contract_version()` tell a seam what a request needs.
  `SandboxedEmbeddingsComponentV1` answers a media request for a package that does not declare `media` with a capability
  error (400, zero calls into the guest). A host with its own seam applies the same rule.
- **Gate ①.** The capability word `media` joins the embeddings vocabulary. A package declaring it must declare
  `contracts: {"embeddings": 2}`, or gate ① refuses it with `ManifestErrorV1::MediaCapabilityRequiresContract2`. A host
  whose range lacks 2 refuses a contract 2 package through the existing range handshake; contract 1 packages keep
  working on a host that admits `{1, 2}`.
- **Gate ②.** `south.embeddings-component.v1` (still version 1) requires the row `embeddings.request.media` of a package
  that declares `media`, and of no other; its assertion is that the media input's `data` appears in the descriptor body
  unchanged. The new check `MediaInputsFollowTheDeclaration` judges every request case holding media: a declaring package
  builds it or refuses it with a capability error (a model that takes none); any other package refuses it with a
  capability error. `ReferenceIntegrity` is not part of contract 2 (there are no reference nodes). The OpenAI-compatible
  and Vertex packs gain `embeddings.request.refused-media`.

## 3. E-O2: the guest memory and the inline bound (ruled by lv, 2026-10-09)

The bound first ruled was the runtime's 16 MiB payload limit applied to the request view. Measurement showed it does not
fit the default sandbox (the data is in the embeddings record §17.10; the 64 MiB failures are the justification of the
ruling): with the default 64 MiB of guest memory a single media input above **7.9 MiB** of base64 (8,253,128 characters,
10.6 ms) traps on guest memory, and the guest's working memory is 8 to 12 times the payload. The same near-16 MiB request
builds in 21 ms with 192 MiB. The prepared frame is also longer than the view and the runtime limits the frame to 16 MiB.
lv ruled option 2: **more guest memory as host-side configuration**, south's default `RuntimeLimitsV1` unchanged.

**Host obligations** for a host that admits a package declaring `media`:

1. Build the embeddings-world runtime with guest memory of at least **192 MiB**:
   `south_contracts::EMBEDDINGS_MEDIA_GUEST_MEMORY_BYTES`, or `RuntimeLimitsV1::for_embeddings_media()` in
   `south-provider-runtime` (the default limits with only the memory raised). The 192 MiB runtime serves contract 1
   packages unchanged.
2. Answer 413 before admission a request whose serialized view is above **15 MiB = 15,728,640 bytes**
   (`south_contracts::MAX_EMBEDDINGS_REQUEST_VIEW_BYTES`).

Measured at the bound in a 192 MiB runtime (release mode, default 2 s deadline):

| Request | View | Prepared frame | Margin to 16 MiB | Sandbox |
|---|---|---|---|---|
| 1 input | 15,728,640 B | 15,729,069 B | 1,048,147 B | 24.5 ms |
| 2 inputs | 15,728,634 B | 15,729,207 B | 1,048,009 B | 22.9 ms |
| 2048 inputs | 15,726,724 B | 15,927,811 B | 849,405 B | 33.9 ms |

The margin carries about 500 bytes of dialect wrapper per input at 2048 inputs; Gemini's is about 100 (the model name
repeats in every batch item). `inline_bound::a_request_at_the_inline_bound_builds_in_the_media_runtime` repeats the
one-input row through the sandbox seam with the exported constants in the ordinary suite.

## 4. The Gemini package and the native arm

`embeddings-gemini` 1.1.0: capabilities `batch`, `dimensions`, `embed`, `media`; `contracts: {"embeddings": 2}`;
`south_runtime` **0.51.0**, the first runtime whose gate ① admits `media` (`the_gemini_package_declares_the_first_runtime_with_media_and_contract_2`:
a host claiming 0.50.0 refuses it through the declared runtime, a host whose range lacks 2 through the contract number).
It is a minor: text behavior is unchanged.

The body is transcribed from the native arm (`openai_embeddings_to_gemini`, `proxy_gemini_embeddings`,
`estimate_media_tokens`). Every input is one request object with one part: `{"text": …}` or
`{"inline_data": {"mime_type": <media type>, "data": <the client's string>}}`; a single input goes to `:embedContent`, an
array to `:batchEmbedContents`, text and media mixed; `outputDimensionality` is on every item. The fallback estimate
adds 512 for `audio/*`, 1024 for `video/*` and 258 for the rest; `max_input_tokens` equals it.

**Intentional differences from the native arm** (embeddings record §17.9, §11): a `data:…;base64,…` string whose media
type breaks the §3 grammar is text under contract 2 (natively it was media); the inline bound is 15 MiB where the native
arm accepts up to the host's 32 MiB JSON body; the model is percent-encoded in the URL; and the differences of §11 stand.

**Open item E-O1.** The component refuses media for the model `gemini-embedding-001` with a capability error. That is the
one model the native arm hard-codes as text-only, carried over and marked as a known hard-code in the reference and in
§17.5. §3 of the record wants this fact to be data (a dialect word on the model row or a catalog entry), but no channel
carries it to an embeddings component today. It stays open for lv until a channel exists.

## 6. Hosts

Breaking only for a host that wants the Gemini component's media: a host must list contract 2 in its embeddings range,
parse with `parse_embeddings_request_v2` for packages declaring `media`, build the 192 MiB runtime and answer 413 above
15 MiB (§3). A host that does none of that keeps every contract 1 package, because contract 1 behavior and wire shapes are
unchanged; it cannot load `embeddings-gemini` 1.1.0 (the range handshake refuses contract 2) and stays on 1.0.2. Public
enums gained variants (`EmbeddingInputV1::Media`, `ManifestErrorV1::MediaCapabilityRequiresContract2`,
`CheckV1::MediaInputsFollowTheDeclaration`), a source break for exhaustive matches, which is why the three crates took a
minor. `compatibility.json` still records `embeddings_v1` as `not_verified` for both hosts.
