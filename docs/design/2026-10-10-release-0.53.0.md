# Release 0.53.0: `decode_sse_v1` in the host-only crate `south-host-grammars`

Status: prepared on branch `release/0.53.0` (based on `origin/main` `a67c2a0`, which merged #174); not tagged. The tag
and the host re-pins are separate steps.

Date: 2026-10-10

Records: [boundary record](2026-09-30-host-zero-vendor-boundary.md) §13.13 (the crate, the decoder and why it is not in
`south-contracts`), §13.12 (Q47), [release 0.52.0](2026-10-10-release-0.52.0.md).

## 1. What this release carries

Only #174: the new crate `south-host-grammars` with the server-sent events decoder. lv ruled on 2026-10-09 (Q-B6-6)
that it ships early, as a minor of its own, and on 2026-10-10 that it lives in a host-only crate rather than in
`south-contracts` (§13.13). Two consequences lv confirmed on 2026-10-10, recorded in §13.13:

- The Responses component splits its own SSE stream. Under `north_passthrough` the host cuts whole frames with
  `SseDecoderV1::position` and gate ③ "no partial frame" fails closed, so the Responses package (R1) no longer waits for
  the decoder.
- The media worlds' `sse` view entry in `south-contracts`, which takes events the host decoded, ships with the speech
  world's minor. It is not in this release; `build_media_response_view_v1` still refuses the `sse` form.

No component links the new crate, and no guest-linked crate changed: `south-contracts`, `south-provider-api` and
`south-component-conformance` stay at 0.51.0 (#174 touched only files under their `tests/`), so **Q47 does not apply**.
Every package keeps its version, `manifest.json`, `component.wasm` and `south_runtime`; no component lockfile changes; no
contract number changes; the kernel pin is unchanged. The release bump is the workspace-versioned side only
(`[workspace.package] version`, `compatibility.json` `release.version`, the requirements on `south-core`,
`south-testkit`, `south-provider-conformance`, `south-host-grammars` and `south-north-codec`, the literal in
`south-task-core`'s version test, `fuzz/Cargo.lock`).

## 2. API summary

`south_host_grammars` (no dependencies; pure, bounded, never panics):

- `decode_sse_v1(&[u8]) -> Result<Vec<SseEventV1>, SseErrorV1>` for a buffered body.
- `SseDecoderV1` for a stream: `push`, `next_event`, `position` (the stream offset just past the blank line that
  dispatched the last event, so each slice cut there decodes alone to exactly that event), `buffered_len`, `finish`.
- `SseEventV1` (`event`, `data`, `into_parts`; `Debug` shows the data size only) and `SseErrorV1` (`NotUtf8`,
  `LineTooLong`, `EventTooLarge`, `TooManyEvents`, `UndrainedEvent`).
- `MAX_SSE_LINE_BYTES` and `MAX_SSE_EVENT_BYTES` (16 MiB each), `MAX_SSE_EVENTS` (262,144, whole-body function only),
  `DEFAULT_SSE_EVENT_TYPE` (`message`).

The grammar (WHATWG event-stream with three departures), the golden vectors, property tests and fuzz target are in
§13.13. `compatibility.json` lists the crate under `crates` as `sse_decoder_v1`.

## 3. Hosts

Re-pinning to `v0.53.0` is **not breaking**: no existing public item changes; the release only adds a crate. A host
that wants the decoder takes `south-host-grammars` as a git dependency at tag `v0.53.0`, beside its other south crates.
It brings no transitive dependency. A host must not hand it to a component: no component may link it
(`shipped_packages_v1::no_component_links_a_host_only_crate`, `scripts/check-boundaries.sh`).

  release runner and these on macOS (the 0.51.1 record §8 says the same). With the published `component_sha256` values
  replaced by the local ones, the same compare exits 0: nineteen "component.wasm unchanged" and the catalog unchanged.
  The digest-stability check runs for real in the release workflow.
