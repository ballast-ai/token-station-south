# Release 0.73.0: Messages pass-through, forwarded client headers and count tokens

Status: prepared on branch `release/0.73.0`, based on `origin/main` `ca98db8`, which merged #266 (after #261). Not
tagged. Tagging and the host re-pin are separate steps.

Date: 2026-10-17

Records: [Messages pass-through, forwarded client headers, and a count-tokens operation](2026-10-17-messages-passthrough-and-count-tokens.md),
[CI as the verification gate](2026-10-16-ci-as-the-verification-gate.md),
[boundary record](2026-09-30-host-zero-vendor-boundary.md) §13.6 (declared runtime) and §13.12 (Q47),
[release 0.72.0](2026-10-17-release-0.72.0.md).

The change comes from lv's ruling of 2026-10-17 that the host's native `gemini` and `anthropic` provider types are
deleted once their families run on components; the record's Q1–Q6 were ruled as recommended the same day.

## 1. What this release carries

- **#266, Messages pass-through, forwarded client headers and count tokens.** Three gaps stopped the deletion; each is
  closed by a manifest declaration the host reads, with no new WIT function.
  - M1: `north_request_passthrough` admits `messages`, with the Messages wire's request facts (`/max_tokens`, body
    `/model`, body `/stream`). `provider-anthropic` passes Messages through both ways for family `anthropic` only. On
    a `messages` pass-through an upstream error frame and a non-2xx are rendered by the host through the codec (Q2).
  - M2: the provider-world field `forwarded_client_headers` names the client headers a host copies unchanged onto a
    pass-through request (Q3: pass-through requests only); never a reserved, secret or immutable header.
    `provider-anthropic` forwards `anthropic-beta`.
  - M3: the provider-world field `count_tokens` declares the counting operation for one client protocol as one
    path-suffix replacement of the non-stream probe descriptor, applied by the shared `rewrite_count_tokens_path`.
    `gemini`, `vertex-ai` and `anthropic` declare it (Q4); `anthropic-bedrock-invoke` does not (Q6).
  - Gate ② gains `ForwardedHeadersAbsent` and `CountTokensPath`; the delivery suite v2 gains the `messages` protocol
    (20 cases, 43 → 63), and the reference executor implements it.
- **#261, records only.** CI is the verification gate and a verified tree is not verified again. This is the second
  release without a local release replay.

## 2. API changes

- `south-provider-api` 0.60.0 → 0.61.0: `ComponentManifestV1` gains `forwarded_client_headers` and `count_tokens`;
  `CountTokensDeclarationV1`, `PathSuffixV1`, `rewrite_count_tokens_path`, `MESSAGES_OUTPUT_CAP`,
  `MAX_FORWARDED_CLIENT_HEADERS`, `MAX_COUNT_TOKENS_PATH_SUFFIX_BYTES` and `FORWARDING_REFUSED_HEADERS` are new;
  `ManifestErrorV1` gains `InvalidForwardedClientHeaders` and `InvalidCountTokens`.
- `south-component-conformance` 0.71.0 → 0.72.0: the gate ② rows above and the reference metadata versions.
- `south-provider-conformance` (workspace-versioned): delivery suite v2 with the `messages` protocol.
- `south-contracts` (0.56.0) is unchanged. No contract number changes; the kernel pin is unchanged.

## 3. Hosts

**Breaking on re-pin** where `ComponentManifestV1` is built by struct literal or `ManifestErrorV1` is matched
exhaustively. A host must record runtime 0.73.0 in its range to admit `provider-anthropic` 1.3.0, `provider-gemini`
1.4.0 and `provider-vertex` 1.1.0.

`compatibility.json`: the server host's `north_passthrough_delivery_v2` entry is `not_verified`. Its recorded run
described 43 cases; the suite now has 63, and editing the count without a run would fabricate the evidence. The host
re-runs v2 for all three protocols and records the result.

Host follow-up (the record's §3.2, §4.2, §5.2), in the host's own record: serve `POST /v1/messages` on a component row
by pass-through when the package declares it; copy the declared client headers onto pass-through requests; open the
counting routes for families that declare `count_tokens`.

Unverified: the upstream behaviour the record describes (nothing was called against an upstream).

## 4. Package identities

`south-provider-api` and `south-component-conformance` changed, so every package published with 0.72.0 retires
(`messages_passthrough_retires_every_published_072_package_identity`):
- `provider-anthropic` 1.2.6 → **1.3.0**, `provider-gemini` 1.3.16 → **1.4.0**, `provider-vertex` 1.0.6 → **1.1.0**
  (new declarations);
- every other package takes one patch with unchanged behaviour, for example `provider-openai-compatible` 2.11.1.

Declared runtime: `provider-anthropic` 0.67.0 → **0.73.0**, `provider-gemini` and `provider-vertex` 0.60.0 →
**0.73.0** (record §8.1). `ComponentManifestV1` refuses unknown fields, so no earlier runtime parses
`forwarded_client_headers` or `count_tokens`, and no earlier gate ① admits `messages` request pass-through; until the
workspace is 0.73.0 no runtime of that number exists, so the raise lands in this commit, as D7's packages moved to 0.60.0
in release 0.60.0 (#198). The tests that pin these runtimes move with it: `declared_runtime_now` and the twenty-one
retired-identity rows of the three packages in `shipped_packages_v1`, the `provider-vertex` assertion there,
`claude_code_conformance_v1` and `vertex_conformance_v1`. Every other package keeps its `south_runtime`, and no
package's `contracts` move. The release index is expected to list 41 packages and 1 catalog.

## 6. Verification

There is no local release replay (lv, 2026-10-17, #261). The gate is the release pull request's CI run: `quality`
(which on `release/*` branches includes `scripts/check-declared-runtime.sh --build`, the check that each package loads
under the runtime it declares, which the three raises depend on), `crate-versions`
(`python3 scripts/check_crate_versions.py --unreleased`) and `language`. The release workflow itself (build scripts,
gate ② reports, `check-declared-runtime.sh --dist`, the release index and the digest-stability comparison with the
published `v0.72.0` index) runs on the tag.

Local verification on this tree was the fast tier only, each step judged by its own exit code:
- `cargo fmt --all -- --check`;
- `scripts/check-language.sh` (run, and the commits `origin/main..HEAD`);
- `scripts/check-boundaries.sh`;
- `python3 -m unittest discover -s scripts -p 'test_*.py'`;
- `python3 scripts/check_crate_versions.py --unreleased`;
- `cargo metadata --locked --offline --manifest-path fuzz/Cargo.toml` (the edited `fuzz/Cargo.lock` is consistent).

No clippy, nextest, doc build or component build was run locally.

The tag itself is not created here.
