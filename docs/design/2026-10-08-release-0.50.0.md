# Release 0.50.0: the model catalog, `south.model-catalog.v1`

Status: prepared on branch `release/v0.50.0`; not tagged. The tag and the host re-pins are separate steps.

Date: 2026-10-08

Records: [boundary record](2026-09-30-host-zero-vendor-boundary.md) §13.11 (B6-1, the catalog), §13.12 (Q47, the
guest-linked crates' own versions) and §16 Q47–Q49, [released artifacts](2026-09-10-released-component-artifacts.md),
[release 0.49.0](2026-10-08-release-0.49.0.md).

## 1. What this release carries

On top of 0.49.0:

- **The model catalog** (B6-1, #161). `catalogs/model-catalog.json` is published verbatim as
  `model-catalog-v0.50.0.json`, covered by `SHASUMS256.txt`, and listed in `south-release-index.json` under `catalogs`
  as `{ "schema": "south.model-catalog.v1", "file": "model-catalog-v0.50.0.json", "sha256": "d54da284…" }`. This is
  the first release whose `catalogs` is not `[]`. The Rust reader is `south_provider_runtime::ModelCatalogV1`.
- **Q47** (#163). `south-contracts`, `south-provider-api` and `south-component-conformance` carry their own versions
  (0.49.0), so this release, which changes none of them, keeps every package's `component.wasm`.
- The B6-2 design record (#162, proposed; no code).

The kernel pin, the `kernel_contracts` and every south contract number stay as 0.49.0 released them;
`compatibility.json` changes only `release.version`.

## 2. The catalog data

The file is unchanged since #161: the host's export byte for byte (token-station-server
`gateway/src/modules/inference/engine/testdata/model_catalog.v1.json` at `f42bf11b`), SHA-256
`d54da284c6780065def520b8062c109aa6a58a7ab286256fa4621fa8299fecb7`, 28 181 bytes, 37 entries and 60 rules, image and
video models only. Its sources are the host's per-profile sources in `capabilities.rs`, and the host's golden test pins
this exact file against its built-in catalog for 72 probe ids (§13.11 "Initial data"). No entry was added, removed or
re-described for this release, so Q48's per-entry provenance applies to the next data change; the host's loader has
already run over these bytes through that golden test.

## 3. Package identities and `south_runtime`

No package changes. The three guest-linked crates and `components/` are unchanged in source since `v0.49.0`
(`git diff v0.49.0..release/v0.50.0 -- crates/south-contracts crates/south-provider-api
crates/south-component-conformance components/` touches only those crates' tests and the Q47 version lines in their
`Cargo.toml`, which keep 0.49.0). Every package keeps its 0.49.0 version, its `manifest.json` byte for byte, and its
`south_runtime` (0.46.0 for the five provider packages and nine task packages, 0.47.0 for the two embeddings packages
of that release, 0.48.0 for `embeddings-vertex`). Each declaration is at most 0.50.0, so the release's "no future
runtime" bound admits them, and `scripts/check-declared-runtime.sh` loads each under the runtime it declares, as in
0.49.0.

The release bump follows §13.12 step 1: `[workspace.package] version`, `compatibility.json`'s `release.version`, the
requirements on workspace-versioned crates (`south-core`, `south-provider-conformance` and `south-testkit` in
`south-testkit` and `south-transport-reqwest`; `south-north-codec` in `fuzz/`, with `fuzz/Cargo.lock`), and the
release literal in `south-task-core`'s `rust_library_version_is_independent_of_component_runtime_identity`. The three
crates' versions, the requirements on them, and the seventeen component lockfiles do not change.

## 4. Hosts

Not breaking on re-pin: no public type, enum or contract number changes, and no package identity changes, so a host
that pins packages by digest keeps every pin. A host that wants the catalog discovers it through the index's
`catalogs` entry and verifies it against that entry's `sha256` and `SHASUMS256.txt` (§13.11 "Host consumption").
Under a 0.50.0 tag a host's `Cargo.lock` shows the three guest-linked crates at 0.49.0 and the other workspace crates
at 0.50.0 (§13.12).

## 5. Verification

Run on this tree with workspace version 0.50.0 (macOS; local digests are compared only with local digests), each
judged by its own exit code; the pull request lists every command and its exit code.

- Same-path builds of all seventeen packages (one checkout path, `components/*/target` deleted before the branch
  build): `v0.49.0`, `origin/main` (`ad4f0d1`) and this branch give seventeen identical `component.wasm` digests.
- The release workflow's steps, replayed under the tag `v0.50.0` without publishing: the seventeen gate ② reports
  (each names `south_release` 0.50.0), the Package step (the catalog lands in `dist/` byte-identical to its source),
  and `release_index.py generate --require-gate2-reports` (17 packages; `catalogs` lists `south.model-catalog.v1`,
  `model-catalog-v0.50.0.json`, `d54da284…`).
- `release_index.py compare` against an index generated by `origin/main`'s script under `v0.49.0` over the same
  builds, without catalogs as the published 0.49.0 index has none: seventeen packages "component.wasm unchanged", the
  catalog new, no violation. Against the published `v0.49.0` index (checksum verified) every version and every
  `manifest_sha256` match; the `component.wasm` digests differ only because a local build never reproduces the release
  CI's, so that comparison is meaningful only in release CI, where the same toolchain and unchanged sources and
  lockfiles are expected to reproduce the 0.49.0 bytes.
