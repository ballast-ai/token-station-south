# Release 0.48.0: the embeddings value channel and `embeddings-vertex`

Status: prepared on branch `feature/embeddings-vertex`; not tagged. The tag and the host re-pins are separate steps.

Date: 2026-10-08

Records: [embeddings contract](2026-09-30-embeddings-contract.md) §16 (the value channel in this world, the Vertex
rows) and §11 (intentional differences), [boundary record](2026-09-30-host-zero-vendor-boundary.md) §13.6 (the
declared-runtime discipline) and §13.8 (the value channel), [release 0.47.0](2026-10-08-release-0.47.0.md).

## 1. What this release carries

On top of 0.47.0: gate ① admits the value channel in the `embeddings-adapter-v1` world (§2), and the third embeddings
package, `embeddings-vertex` (§3), which needs it. The kernel pin, the `kernel_contracts` and every south contract
number stay as 0.47.0 released them; `compatibility.json` changes only `release.version`.

## 2. Gate ①: the value channel in the embeddings world

The record's §6 has Vertex take its project and region from non-secret configuration or minted exported attributes,
which assumes the Q14 value channel (boundary record §13.8). 0.46.0 shipped that channel for the provider world only,
and 0.47.0's gate ① refused `config_schema` and exported credential attributes on an embeddings package, as on the
task worlds. `build-embeddings-request` receives a `ProviderConfig` too, and the embeddings host already mints the slot
and obtains the exported attributes before it builds the request (record §9 step 1), so this release admits the two
sources of `ProviderConfig.declared`, and nothing else (record §16):

- **Admitted.** A family's `config_schema`, under the provider world's key rules, and `attributes` on credential
  recipes. Both reach `declared` through `ComponentManifestV1::declared_keys` / `declared_values` exactly as in the
  provider world, and the one-namespace rule (D8) applies.
- **Still refused.** `endpoint`, `host_values` (it lives on `ChatRequest`, which this world does not have), the
  instance declarations, `signing`, `stream_framing`, `usage_evidence` and `request_facts`.
- **The task worlds are unchanged.** They still refuse `config_schema` and credential attributes.
- **Gate ②.** `south.embeddings-component.v1` gains the provider suite's `UndeclaredValuesIgnored`: every request case
  is rebuilt with one undeclared key added to `provider_config.declared` and must give the same answer. Additive, so
  the suite stays version 1; the 0.47.0 embeddings packages pass it unchanged.

The 0.47.0 runtime refuses an embeddings manifest that declares either source, so a package that uses the widening
declares `south_runtime` 0.48.0, the oldest runtime that admits it.

## 3. `embeddings-vertex`

| Package | Version | Families | Auth arms | Capabilities |
|---|---|---|---|---|
| `embeddings-vertex` | 1.0.0 | `vertex-ai` | `bearer` | `embed`, `dimensions` |

Vertex AI's `:predict` dialect, transcribed from the host's native Vertex arm: one text input per request (a batch or
a token-id input is a capability error before admission, whitespace-only text a 400),
`{"instances": [{"content": …}]}` with `parameters.outputDimensionality` for `dimensions`, the vector locator
`Array { /predictions, /embeddings/values }`, immutable paths `["instances"]`, no fallback estimate, and usage
`Reported` as the sum of each prediction's `statistics.token_count` (or `tokenCount`) rounded half away from zero,
with `per_input_tokens`; a missing, negative or non-numeric count is a protocol error. Upstream errors map as the
Gemini package's. Its fixture pack's README (`fixtures-embeddings-vertex/`) cites the native code each expectation
comes from.

**Values.** Config keys `region` (required) and `project` (optional, the operator's override), and the exported
attribute `project_id`, from the non-secret field the service-account key file's `/project_id` imports. The component
uses `project` before `project_id`, the native arm's order.

**The credential recipe** reproduces the host's Vertex mint: an RS256 `jwt_sign` step over the key file's
`private_key` with `iss` = `client_email`, `scope` = `https://www.googleapis.com/auth/cloud-platform`, `aud` = the
token step's endpoint, `iat` = now and `exp` = now + 600, then an `oauth2_token` form step (`grant_type` jwt-bearer,
`assertion`) to `https://oauth2.googleapis.com/token`, presenting `access_token` until `expires_in` later. It does not
rotate, and 4xx / 5xx take the defaults (`reauth_required` / `transient`), the host's classification.
`refresh_margin_seconds` 300 is the host's refresh buffer; gate ① requires the margin to be shorter than the shortest
validity, so the recipe declares `min_ttl_seconds` 301, which changes nothing for Google's 3599 s tokens. Recipes are
enabled only for first-party packages verified by digest (boundary record §3.4 rule 5), and the operator confirms the
one endpoint.

**Base URL and confinement.** The host passes the location's API origin as `base_url`
(`https://{region}-aiplatform.googleapis.com`, or `https://aiplatform.googleapis.com` for `global`), and the component
appends `/v1/projects/{project}/locations/{region}/publishers/google/models/{model}:predict`, each value one
percent-encoded segment, so `EndpointConfinement` holds unchanged. A base URL that is a Vertex AI origin other than the
location's is refused before admission (a 500 naming both); any other base URL (a proxy, a test server) is used as
given.

**Intentional differences from the native arm** (record §11): model, project and region are percent-encoded segments
(identical for `[A-Za-z0-9._-]`); more predictions than inputs is refused by the host's checks, where the native arm
billed and returned only the first; a single token-id sequence is a token-id refusal, where the native arm counted its
integers as inputs (both 400 before admission); a configuration without its region or project is a 500 naming the key,
where the native arm answered 400; and a mismatched Vertex AI base URL is refused, where the native arm derived the
host from the region and ignored the row's URL.

`compatibility.json` records `embeddings_component_capabilities` `embeddings_v1` as `not_verified` for both hosts; a
gate ② pass is not host adoption.

## 4. Package identities and `south_runtime`

`embeddings-vertex` declares `south_runtime` 0.48.0, and a host claiming 0.47.0 refuses it through the declared
runtime alone (`the_vertex_package_declares_the_first_runtime_with_the_embeddings_value_channel`).

The gate ① change and the Vertex reference changed `south-provider-api` and `south-component-conformance`, which every
guest links. A same-path rebuild of the sixteen other packages at `v0.47.0` and on this branch before the release
commit (workspace still 0.47.0) gave a different `component.wasm` for every one (a clean rebuild of the same tree is
byte-identical), so each published 0.47.0 identity retires, or the release's digest-stability check would refuse it
(`the_embeddings_value_channel_retires_every_published_047_package_identity`). Their behavior is unchanged and none
needs anything newer, so each keeps its `south_runtime`, and `scripts/check-declared-runtime.sh` loads them in
checkouts of `v0.46.0` and `v0.47.0`.

## 5. Hosts

Not breaking on re-pin: no existing public type, enum or contract number changes (the one addition is the module
`south_component_conformance::reference_vertex_embeddings`); gate ① admits more in one world, and the embeddings suite
runs one more check. A host that routes `embeddings-vertex` builds `declared` per attempt for this
world as the boundary record's §13.8 lists for the provider world (`declared_values` from the row's config values and
the selected credential's exported attributes, no other key, and any client-supplied value that collides with a
declared key stripped), runs the package's credential recipe, and passes the location's API origin as `base_url`.
